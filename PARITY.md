# List parity: React vs Vue

Vue is the reference. Each row is a place where `packages/react` behaves or is shaped differently from `packages/vue`; the fix is to make React match, unless the Vue column says otherwise. Compared against the code at commit `1b91ee8`, from reading both packages (not from running them).

Priority: **High** gives a consumer wrong data or wrong requests. **Medium** is a behaviour or API difference a consumer can run into. **Low** is internal or cosmetic.

## Root component (`list.tsx` vs `list.vue`)

| Priority | Difference                                                                                            | React                                                                                                                                                                                        | Vue                                                                                                                                                                |
| -------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| High     | `refresh` in load-more mode, already on page 1                                                        | Clears the rows and sets page 1, which is no change, so no request starts and the list stays empty                                                                                           | Clears the rows and always fetches page 1                                                                                                                          |
| High     | `stateManager.set` after a response                                                                   | Gets the `state` of the render that started the request: the old `rows`, `count` and `response`                                                                                              | Gets a snapshot taken after the response is stored                                                                                                                 |
| High     | A filter change while not on page 1 (`setFilter`, `setFilters`, `clearFilters`)                       | Sends two requests: the query effect fetches with the old page, then the filters effect sets page 1 and fetches again. `before*` and `requestHandler` run twice                              | One request, on page 1                                                                                                                                             |
| High     | Restore at mount (`stateManager.get` returned `filters`)                                              | `onFiltersChange` never fires (it compares the pre-restore filters with the defaults), and `stateManager.init` receives the pre-restore state                                                | `init` receives the restored state, and `onFiltersChange` fires when the restored filters differ from the initial ones                                             |
| Medium   | When `stateManager.get` runs                                                                          | In the mount effect, after the first render, with no `try/catch`: the first paint and server render show unrestored values and a throwing `get` breaks the component                         | In setup, before the first render, inside `try/catch`                                                                                                              |
| Medium   | `requestTrigger` for `refresh` and `clearState`                                                       | Stale: the request starts in the same render, so the trigger is still the previous one                                                                                                       | Set before the request reads it                                                                                                                                    |
| Medium   | Actions before the first response (`setPage`, `setPerPage`, `setSearch`, `setSortBy`, `setSortOrder`) | Change state without a request: the query effect does not run until the first request has finished                                                                                           | Fetch right away. Only the `filters` and `columns` watchers wait for the first response                                                                            |
| Medium   | `setPage(page)` with the page already shown                                                           | No request: the state does not change, so the query effect does not run                                                                                                                      | Refetches that page                                                                                                                                                |
| Medium   | `clearState`                                                                                          | Calls `stateManager.clear`, then fetches                                                                                                                                                     | Calls `stateManager.clear`, then runs `init`: `stateManager.init`, `onFiltersChange` if the saved filters differ, then fetches (skips the fetch for a seeded list) |
| Medium   | A hook that throws (`onResponse`, `afterPageChange`, ...)                                             | Runs inside the request's promise chain, so the throw becomes the list's `error`, clears `rows` and fires `onError`                                                                          | Vue reports it to the app's error handler; the response stays                                                                                                      |
| Medium   | Identity of `state` and `context`                                                                     | `state` is a new object on every render, so `context` and the `ref` handle change on every render and every `useListContext()` consumer re-renders                                           | A stable reactive object                                                                                                                                           |
| Medium   | React StrictMode                                                                                      | The mount effect guard reads state, so `stateManager.get` and `stateManager.init` run twice in dev. The seeded first request is not repeated: the mount effect cleanup clears `isStartedRef` | Runs once                                                                                                                                                          |
| Low      | `filters` prop after setup                                                                            | `defaultFilters` is rebuilt from the current prop on every render, so `clearFilters` resets to the latest prop                                                                               | Read once at setup, as documented                                                                                                                                  |

## Not tracked here

These differ because the frameworks differ, not because the code drifted:

- Hooks are props in React (`onResponse`) and emits in Vue (`@on-response`); the event map is shared in `shared/types/events.ts`.
- React passes `children` as nodes or a render function; Vue uses slots and `v-bind`.
- The imperative handle is a `ref` prop with the context in React and `defineExpose(toRefs(context))` in Vue.
